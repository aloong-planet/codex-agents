# 运行状态并行时间轴设计审查

## 结论

方案可实施，但必须坚持“状态持续”和“请求执行”是不同概念，不能把 `typing_start` 请求画成与 Codex 并行。

## 审查发现与处理

1. **只画现有六行的甘特条仍会误导。** `typing_start` 只是启动请求，真正跨越 Codex 的是启动成功后的 typing 状态。设计改为 typing 复合泳道。
2. **typing 启动失败时不能画持续状态。** 以 `typingDiagnostics.sendStart.outcome === completed` 为门禁；旧记录缺诊断时保守不画持续片段。
3. **短阶段会在长 Codex turn 中不可见。** 仅增加 CSS 最小可见宽度，不改计算比例和重叠数值。
4. **时间轴和串行列表同时展示会重复且语义冲突。** 精确耗时不能删除，但应归入对应泳道的可展开详情；只有旧记录缺少时间轴数据时才回退串行列表。
5. **运行中时间轴会随轮询变化。** 纯计算 seam 使用调用时的 `Date.now()`，不持久化派生位置。
6. **旧记录可能没有完整时间戳。** 数据不足时隐藏时间轴，而不是发明顺序。
7. **轮询重绘会重置原生 details。** 展开 lane 以 `runId` 为键保存在浏览器内存；用户选择优先于默认规则，并在 run 消失时清理。
8. **三个独立折叠区可能同时展开，重新造成长页面。** 打开一个泳道时关闭同 run 的其他泳道。
9. **按最长跨度默认展开会反复选中 typing 包络。** 默认选择改成固定的 Codex；它是用户最常诊断的核心阶段，也不会随某次网络耗时变化而跳动。
10. **把接收与排队合成一张前置卡片会掩盖两个独立串行阶段。** 两者恢复为独立行；视觉结构与主泳道一致，但不提供没有明细的空展开区。
11. **处理回执并不总是前置阶段。** 它只在 typing 不可用时发生，因此只在真实 timing 存在时单独显示，不能归入“接收与排队”。
12. **旧图例重复解释了已经可从条形位置读出的关系。** 改为只说明时间对齐和点击入口，不再列 typing 状态机或固定某一对阶段的重叠时长。

审查后没有需要用户补充的产品决策。
