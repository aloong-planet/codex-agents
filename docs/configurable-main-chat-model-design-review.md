# 主微信会话模型配置设计审查

更新时间：2026-08-21

## 审查结论

方案可以进入实现，但必须保留以下约束：动态目录解决“新模型可见和可固定选择”，不能被误写成“任何新模型自动成为快速档位”；模型配置必须在入站排队时冻结；模型不可用与超时必须分开处理。

## 已修正问题

### 1. 不能从描述或名字自动判断未来模型档位

当前协议虽有 `modelSpecialty`，本机目录实际为空。依赖 `luna`、`mini`、描述里的“fast”或模型价格进行自动分类都不稳定。设计改为：自动档位使用版本化受审查映射；未知新模型只进入固定列表。

### 2. 不能用 `runtimeProfile` 给主会话换模型

现有 `runtimeProfile` 同时控制 `baseInstructions` 和结构化输出，服务于 Curator。直接复用会把主会话 developer instructions 一并替换。设计改为独立的逐回合 `{model, effort}` 参数和目录读取方法。

### 3. “下一条生效”必须定义消息并发语义

如果在真正调用模型前才读配置，已排队消息会被后来保存的配置改变。设计把模型选择冻结在入站进入队列时，并持久化 config revision 到运行记录。

### 4. 自动探针不能后台静默调用真实模型

自动运行模型能力探针会产生额度消耗，还可能执行工具。第一版只用协议元数据做静态兼容性过滤；真实验证放到 fixture，用户明确测试时才调用真实微信和模型。

### 5. 切换模型不能顺带切换 thread

App Server 支持 `turn/start` 逐回合指定模型。重建 thread 会丢失未进入长期记忆的上下文，不符合用户预期。设计保留 thread，只诚实提示跨模型首回合缓存可能失效。

### 6. 固定模型不能静默回退

用户固定模型表达了明确意图。若下线，应阻止回合并要求重新选择。只有自动档位可以在同一档位的受审查后备映射中降级，并必须显示实际模型。

### 7. 不把所有失败都当作模型下线

超时、连接中断和结果未知时，回合可能已经执行。切换模型后自动重试可能重复工具副作用。只有在回合创建前得到明确模型不可用错误时，才可标记配置不可用；仍不自动重放原消息。

### 8. 常用选项不应在面板宽度下纵向占两行

选择模式和推理强度都是短值、同频操作，保持两列能减少高度且不损失可读性。固定模型是条件字段，显示时独占下一整行；其他通用 `.form-grid` 仍保留原窄屏单列规则，避免扩大改动范围。

## 场景完整性检查

- 首次启动、目录成功或失败。
- 账户未配置、已配置、账户切换、目标切换。
- 固定模型新增、下线、升级提示、effort 改变。
- 自动档位首选可用、后备可用、整个档位不可用。
- 保存与排队并发、处理中再次保存、服务重启。
- 旧 v6 状态迁移、损坏目录快照、分页异常和重复模型。
- 模型切换导致缓存冷启动，但 thread 和历史保持。
- 明确不可用、启动前失败、启动后失败、超时和未知结果。

未发现需要用户继续决策的设计分支。默认采用按账户、自动快速、Luna + low；实现阶段不得扩展到 Curator、日报或全局 Codex 配置。
