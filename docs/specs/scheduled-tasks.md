## Problem Statement

The AI daily news job has dedicated scheduling and recovery. At the start of this feature, users could not describe another recurring task, inspect its settings, or enable and disable it through a shared conversational management capability. A generated result, its delivery attempt, and the task's enabled state must remain distinguishable so that recovery does not generate duplicate messages or stale waiting labels.

## Solution

Let the main Weixin Codex turn translate explicit user intent into validated management operations. The service persists task settings, claims due occurrences, executes bounded task instructions, saves the complete output, and delivers it to the original account and conversation. Management receipts describe the stored result, not an intended operation.

Proposed first-release scope: one-time reminders, fixed-interval tasks, and calendar-based text research/report tasks, with listing, inspection, editing, enable/disable, deletion, explicit run-now and history. The existing daily news becomes a managed task while retaining its specialised content template and stored results. This is a reusable product capability; it does not create a particular new live task by itself.

## Functional Requirements

### scheduled-tasks::REQ-001 Conversational management

- scheduled-tasks::REQ-001/AC-01: An explicit, sufficiently specified request creates a persisted task and returns its identity, instruction, resolved schedule, timezone, enabled state, destination and next execution time.
- scheduled-tasks::REQ-001/AC-02: Listing and inspection remain within the trusted owner scope. With bound personal channels, default listing uses the reception conversation and explicit all-channel listing follows [channel-switching::REQ-004/AC-04](channel-switching.md); an empty list is reported explicitly, and multiple name matches require clarification before mutation.
- scheduled-tasks::REQ-001/AC-03: Missing, contradictory or invalid settings produce a targeted clarification/error without creating or partially modifying a task. A persistence failure is not reported as success.
- scheduled-tasks::REQ-001/AC-04: Schedule forms are a one-time instant or relative one-time delay, positive fixed interval and calendar recurrence in an explicit IANA timezone (default Asia/Shanghai, displayed in the receipt). A request for a delay without recurrence executes once, not at repeated intervals. Resolve a relative delay once at acceptance and retain the resolved instant on replay. Past one-time dates and invalid delays/intervals are rejected; ambiguous natural-language dates are clarified. For calendar daylight-saving changes, a nonexistent local time is skipped and a repeated local time produces one occurrence at the earlier instant.
- scheduled-tasks::REQ-001/AC-05: A fixed interval persists a first execution instant and duration; slots are first instant plus whole multiples of that duration. With no explicit future start, the first instant is the accepted creation time plus one interval. Completion, restart, name/content edits and pause do not move this anchor. Re-enable chooses the next future slot, while downtime uses latest-only catch-up. Interval/calendar rule changes establish a new cadence revision; an interval edit without an explicit start first runs one new interval after the accepted edit. The receipt shows that first/next instant. Calendar recurrence remains local wall-clock time in its named timezone, not an elapsed-duration interval.

### scheduled-tasks::REQ-002 Settings revisions

- scheduled-tasks::REQ-002/AC-01: Editing name, instruction or schedule updates the task atomically and returns the stored settings, including its resulting next execution time; a conflicting revision requires rereading rather than silently overwriting a concurrent change.
- scheduled-tasks::REQ-002/AC-02: Editing does not implicitly enable a paused task. An already claimed occurrence and its cached body retain their frozen settings revision; a schedule edit takes effect only for future unclaimed occurrences and does not backfill the old schedule. An already claimed one-time automatic plan cannot be rearmed by editing its time; use a new task or an explicit independent run-now.

### scheduled-tasks::REQ-003 Enable and disable

- scheduled-tasks::REQ-003/AC-01: Disabling a task stops future automatic execution and delivery of existing caches, including a manual result authorised before this disable. Each explicit disable advances a durable pause generation, even when the task is already paused; replaying the same management operation does not advance it twice. Before each new submission, the latest task state and pause generation are checked atomically with its claim. Already-submitted external operations may settle and are recorded; the receipt does not promise recall.
- scheduled-tasks::REQ-003/AC-02: Enabling a task resumes future scheduling and eligible cached delivery without replaying terminal delivery results. Paused time is intentional, not downtime to backfill; an overdue one-time task requires an explicit new time or run-now.

### scheduled-tasks::REQ-004 Explicit run and removal

- scheduled-tasks::REQ-004/AC-01: Proposed run-now creates one distinct manual occurrence without changing the recurring plan or enabled state, including for a paused task. It captures the current pause generation and permits only its own delivery while that generation remains current. A later explicit disable revokes the exception. A new run-now after that disable can authorise its own result; unrelated automatic backlog remains paused. Busy or capacity-limited requests return an actionable refusal, not a false started receipt.
- scheduled-tasks::REQ-004/AC-02: Proposed deletion stops future execution and delivery, retains inspectable history, and never rewrites past attempt outcomes. Unsubmitted pending results become cancelled-by-task-deletion, not delivered, and are subject to settled-detail retention under REQ-014. If an operation is in flight, reject deletion with a clear explanation and offer disable; deletion becomes available after settlement, including settlement to unknown on restart. Enabling cannot undo a deletion: a deleted task refuses every later edit, enable or run, and a new task takes its place.

### scheduled-tasks::REQ-005 Durable occurrence ownership

- scheduled-tasks::REQ-005/AC-01: A due occurrence is durably claimed before execution, with a stable identity and frozen task revision; duplicate scheduler wakes and replayed management calls cannot create a second effective occurrence for the same request.
- scheduled-tasks::REQ-005/AC-02: A task does not execute overlapping occurrences. Proposed downtime or busy/capacity recovery starts only the most recent missed occurrence; older missed slots are recorded as compact skipped ranges with cadence revision and time boundaries, rather than one row per elapsed slot. Existing generated caches remain intact. Intentional pause is excluded from catch-up; a skipped/unknown occurrence never becomes a new candidate later.
- scheduled-tasks::REQ-005/AC-03: Restart restores settings, enabled state, claimed occurrences and cached results. A claimed execution whose completion cannot be reconciled becomes execution-unknown, not an automatic replay; later recurring slots remain eligible.
- scheduled-tasks::REQ-005/AC-04: A one-time scheduled occurrence is claimed at most once. Completing or failing it does not automatically schedule another execution or discard its pending cached result.

### scheduled-tasks::REQ-006 Bounded execution and caching

- scheduled-tasks::REQ-006/AC-01: A scheduled execution has its own context and lifetime, independent of the creating chat turn; first-release templates provide reminders or researched text results. It does not fabricate a Weixin inbound message or take ownership of an unrelated chat reply.
- scheduled-tasks::REQ-006/AC-02: A complete generated message is persisted before channel submission. Channel credential/context failures preserve that exact message for recovery and do not rerun content generation.
- scheduled-tasks::REQ-006/AC-03: Failure or timeout before output exists records execution failure and its stage without inventing a deliverable. Proposed generic tasks do not automatically rerun that failed occurrence; an explicit run-now or the next scheduled occurrence is separate. The existing daily-news research retry policy remains governed by its own specification.

### scheduled-tasks::REQ-007 Delivery recovery

- scheduled-tasks::REQ-007/AC-01: All scheduled-task results for one trusted account/conversation share a serial dispatcher. It atomically selects and claims the oldest currently eligible cached occurrence by original planned instant, then stable occurrence identity; manual runs use their accepted request instant. Live target, task, pause-generation and channel checks are part of the claim. Paused/ineligible tasks do not block other tasks. A result not yet generated does not reserve delivery order. Recovery never substitutes another account or recipient.
- scheduled-tasks::REQ-007/AC-02: Reconcile current prerequisites after each persisted attempt outcome, startup and trusted credential/context update, using durable current channel state. If an old attempt fails after a usable fresh context arrived, retain its historical failure but clear the current waiting label and enqueue a recovery wake immediately. A committed replacement binding advances the credential generation; a no-op already-connected response is not a refresh; only conversation context valid for that generation can unblock delivery. The current provider clears context on rebind, so a message received before rebind is insufficient. An old-generation authentication error cannot invalidate newer credentials. Paused tasks retain caches; only a still-valid post-pause manual grant may send.
- scheduled-tasks::REQ-007/AC-03: Accepted, partial, nonrecoverable rejected and unknown submissions are terminal for automatic replay. A channel interruption after submission begins is unknown unless authoritative reconciliation establishes an outcome; it is never inferred to be a safe failure.
- scheduled-tasks::REQ-007/AC-04: A prerequisite failure or nonaccepted submission stops the current drain and blocks its captured credential/context generation for further automatic submissions. A newer valid generation may start a separate recovery drain for eligible pending messages, even if it arrived before that failure settled. Recoverable prerequisite waits are allowed only with authoritative evidence that no part was accepted; partial or uncertain sends obey scheduled-tasks::REQ-007/AC-03. Attempt evidence remains separate from the current blocker.

### scheduled-tasks::REQ-008 Observable outcomes

- scheduled-tasks::REQ-008/AC-01: Task detail/history separately show enabled state, next execution, each occurrence's planned time, execution result, delivery result, reason and required recovery action; task identity remains stable after a rename or deletion. History pages are ordered by planned instant descending with a stable identity tie-break. Counts distinguish retained occurrence records from cumulative executions, with historical completeness disclosed; an optional occurrence identity narrows the query only within the same trusted task.
- scheduled-tasks::REQ-008/AC-02: Receipts derive from current stored state. They do not claim to wait for a resolved prerequisite, promise backlog when none is eligible, equate channel acceptance with phone receipt, or call an execution successful merely because it was scheduled.
- scheduled-tasks::REQ-008/AC-03: Proposed failure notifications describe the stage and actionable cause, coalesce unchanged blockers rather than sending an hourly duplicate, and record their own delivery outcome without recursively generating failure notifications or replaying unknown notifications.

### scheduled-tasks::REQ-009 Existing daily news

- scheduled-tasks::REQ-009/AC-01: Proposed unified management exposes, in personal chats, the existing daily-news identity, schedule, enabled target, cached messages and delivery outcomes without duplicate import, content regeneration, historical outcome resets or changes to its content requirements.
- scheduled-tasks::REQ-009/AC-02: Migration allows at most one active owner of a news occurrence and its cached delivery; a fenced transition may have zero active owners until reconciliation completes. Stop/fence legacy generation, retry and drain, settle in-flight work, durably commit the identity/body/outcome import and ownership record, then activate the new owner. Restart never enables both or automatically falls back after the ownership commit. Existing news commands and general management use the same committed owner; while ownership is unresolved, mutations/execution report reconciliation pending.

### scheduled-tasks::REQ-010 Reminder ownership

- scheduled-tasks::REQ-010/AC-01: An explicit reminder accepted as a scheduled task must not independently become an effective duplicate through memory plan extraction. A durable link identifies that specific intent and scheduling owner before either subsystem can activate it; concurrent extraction, replay and restart consult the same ownership decision.
- scheduled-tasks::REQ-010/AC-02: Editing, pausing or deleting that task cannot revive the linked memory reminder. Retain the ownership tombstone after deletion. Other future plans in the same message and unrelated memory follow-ups retain their existing behavior; do not suppress the whole message as a deduplication shortcut.

### scheduled-tasks::REQ-011 One-time completion and history

- scheduled-tasks::REQ-011/AC-01: A one-time task is completed only after its single occurrence has succeeded and its entire delivery is channel-accepted. Creation, exhaustion of its schedule, running generation, saved output and an in-flight submission are not completion. Queries expose a lifecycle outcome separately from the enabled setting and preserve the distinction between channel acceptance and phone receipt. Failed execution, partial or rejected submission, and uncertain execution/submission expose their own outcome and required action, never successful completion. A later success does not hide an unresolved older execution: the task's outcome reports the unresolved one first.
- scheduled-tasks::REQ-011/AC-02: Default task listing omits deleted tasks and completed one-time tasks while retaining scheduled, running, pending-delivery and unsuccessful/uncertain tasks. Users can explicitly list completed tasks or all tasks; counts and pagination apply to the chosen view. An empty default list with retained completed tasks means no current tasks, not no saved history. Inspection by identity/name and full-text/history reading remain available for completed tasks and remain scoped to the trusted owner; the current-channel listing boundary follows [channel-switching::REQ-004/AC-04](channel-switching.md).
- scheduled-tasks::REQ-011/AC-03: Completion is a retained historical classification, not automatic deletion or pause. Existing persisted tasks receive the same classification without recreating them or changing their enabled setting, body, attempts, occurrence claim or intent ownership. Restart, repeated query, prerequisite recovery and replay of the original creation cannot reopen a completed occurrence; replay receipts show its current classification. Pending cached output stays eligible for ordered recovery under the existing delivery rules.

### scheduled-tasks::REQ-012 Receiver-facing reminder text

- scheduled-tasks::REQ-012/AC-01: On creation or an explicit content edit, the main model separates schedule/delivery settings from a complete natural reminder addressed to the recipient. Preserve actors, action, negation, quantities, deadlines, quotation and requested language without inventing advice. `每分钟提醒我活动一下` produces `你应该活动一下了`; semantic ambiguity requires clarification before mutation, not a guessed recipient or date.
- scheduled-tasks::REQ-012/AC-02: An explicit verbatim request preserves its specified payload character-for-character, including whitespace and line breaks, without pronoun rewriting or an automatic title. The host validates that verbatim text occurs within the exact source fragment; invalid or empty content does not create or partially edit a task.
- scheduled-tasks::REQ-012/AC-03: New reminders save semantic instruction and final body separately; content edits save both together atomically. A missing final body is not silently replaced with management text. Body limits apply before saving without truncation. Name/time-only edits and enable/disable preserve the body.
- scheduled-tasks::REQ-012/AC-04: Creation/content-edit receipts show the exact stored complete outgoing body alongside existing settings. Inspection and paged text access expose that same body; receipt wording must not rephrase it or require a second routine approval.
- scheduled-tasks::REQ-012/AC-05: Static reminder occurrences copy the saved body into their frozen cached output and send it without per-occurrence model rewriting or title framing. Existing delivery recovery reuses that cache under scheduled-tasks::REQ-006/AC-02 and scheduled-tasks::REQ-007.
- scheduled-tasks::REQ-012/AC-06: Existing tasks lacking the explicit body keep their legacy rendering until an explicit content edit. Metadata edits, restart and enable never silently normalize them. Already claimed occurrences, cached bodies and delivery outcomes keep their frozen content; a content edit does not change pause state or cadence. Durable replay cannot overwrite the saved body with a new paraphrase.

### scheduled-tasks::REQ-013 Current configuration authority

- scheduled-tasks::REQ-013/AC-01: A request that only queries, refreshes delivery prerequisites or executes an existing task preserves its settings and revision. The main model uses current stored settings even when recalled memory or older conversation asks for a different scope. Explicit editing followed by execution remains supported; only the requested fields change.
- scheduled-tasks::REQ-013/AC-02: Managed task settings have one authoritative store. Memory curation does not create a second active settings record. When it identifies an existing memory as task-owned, it retires only that matched memory against a host-provided task identity, retaining the original value and ownership evidence for audit. Mixed personal preferences remain active; ambiguous matches and missing task authority do not retire anything.
- scheduled-tasks::REQ-013/AC-03: Task ownership context comes from the current account and the originating conversations. Retired settings stay out of active recall/search after restart or task deletion. Failed or conflicting memory writes cannot falsely report retirement or partially remove unrelated facts.

### scheduled-tasks::REQ-014 Permanent execution summaries

- scheduled-tasks::REQ-014/AC-01: Do not delete occurrence summaries by count or age. Count distinct accepted executions cumulatively, excluding compact skipped ranges; replay/retry of the same occurrence does not increment it. For existing/imported tasks with potentially pruned history, report the known minimum rather than a fabricated lifetime total. Preserve summaries across restart and task deletion.
- scheduled-tasks::REQ-014/AC-02: Retain identity, planned time, frozen revision, execution/delivery outcome, failure cause, source/archive outcome and submission-part outcomes after detail cleanup. History and notification queries use bounded database pages, with exact task-scoped lookup and explicit continuation. Missing detail never means missing execution.
- scheduled-tasks::REQ-014/AC-03: Clean only fully settled occurrence details by configurable elapsed retention age or service-wide eligible-detail capacity, oldest eligible settlement first. Defaults are 90 days and 100 MiB; reject invalid configuration. Cleanup atomically removes output copies and detailed research/submission payloads while recording cleanup time/reason and original body size. Paged output reads explicitly report cleared output without regenerating it; an execution that never produced a body remains output-not-found. Existing records begin their retention age when first observed settled after upgrade.
- scheduled-tasks::REQ-014/AC-04: Protect running execution, sending, paused/pending output, unfinished archive work, pending/sending failure notifications and today's retryable automatic news failures. These protected details may exceed the cleanup budget. Do not touch successful article results, local Markdown archives, task settings, request/claim/intent evidence, or notification deduplication. Clearing details never authorizes execution, replay, supplemental delivery or a changed lifecycle.

## Quality Requirements

### scheduled-tasks::QR-001 Bounded execution and protected pending output

Applies to: proposed generic tasks and the shared scheduled-result store after cutover. The following values are the accepted initial defaults. Reminder and researched-text tasks use the implemented generation, body, pending-capacity and minimum-period bounds. Generic research has a 300-second deadline; cancellation retains its reservation until the process stops or the worker is fenced. The daily-news template retains its own stricter content limits and research retry/time policy.

| Resource | Proposed default |
|---|---|
| Minimum recurring period | 60 seconds for interval and calendar rules |
| Active generation | 2 service-wide; 1 per task |
| Generic execution timeout | 300 seconds per occurrence |
| Maximum generated body | 64 KiB UTF-8, including source links and delivery framing |
| Pending/reserved outputs per recipient | 100 messages and 10 MiB body bytes |
| Pending/reserved outputs service-wide | 1,000 messages and 100 MiB body bytes |
| Execution summaries | No count or age deletion |
| Settled execution details | Configurable age/capacity; implementation defaults 90 days / 100 MiB service-wide |

- scheduled-tasks::QR-001/AC-01: Validate recurring schedules against the configured minimum. Admit generation by due/request time with stable identity tie-breaks under global and per-task concurrency limits, including manual execution. Each task contributes at most its latest automatic candidate, so one long backlog cannot monopolise admission. A timeout cancels generic execution without resubmitting that occurrence; active capacity is released only after the old worker stops or is fenced from further work/effects; unavailable capacity is visible in task details and is not falsely called execution failure.
- scheduled-tasks::QR-001/AC-02: Before starting generation, durably reserve one pending slot and the maximum allowed body bytes against both recipient and global quotas. Convert the reservation into exact stored output usage on success, releasing unused bytes; release it after a reconciled no-output failure. At capacity, block new generation, including manual requests, and show usage, limit and the actions that can free capacity. Existing eligible caches may still drain. Freed space wakes latest-only scheduling; intentional pause stays paused. Restart reconciles reservations before admitting more work. Release a no-output reservation only after the former worker has stopped or is durably fenced from storing/submitting a late result; otherwise retain it as reconciliation-pending. Raising/lowering a configured bound never silently removes existing cached output.
- scheduled-tasks::QR-001/AC-03: Reject a generated body beyond the total output budget as output_too_large, with no truncated deliverable and no channel submission. After successful persistence, keep the exact pending body until terminal settlement or explicit task deletion; cleaning settled details must never remove pending/paused bodies. Preserve occurrence claim/high-watermark and management-request/ownership deduplication evidence so cleanup cannot reopen old work. Storage failure halts advancement and sending; never promise that unsaved content is cached.
- scheduled-tasks::QR-001/AC-04: Import every surviving legacy pending body and outcome even when already over the new quota. Block new generation until usage falls below admission thresholds; do not truncate, drop or regenerate imported content. The legacy 31-run pruning policy does not apply to the protected pending store after cutover. Previously pruned content cannot be reconstructed or claimed as migrated.

## Constraints

### scheduled-tasks::CON-001 Trusted boundaries

- scheduled-tasks::CON-001/AC-01: The main Weixin Codex turn owns interpretation of task-management intent; the host validates structured requests and binds account/conversation identities. Business-keyword routing and model-supplied authority/recipient fields cannot bypass that boundary.
- scheduled-tasks::CON-001/AC-02: A scheduled instruction does not grant new module permissions or authorize execution of user files, scripts or binaries. First-release unattended tasks produce text through approved templates and existing capabilities; they cannot recursively create tasks or perform additional outbound effects hidden in fetched content.
- scheduled-tasks::CON-001/AC-03: Disabled accounts/targets and current access revocations are checked before applicable effects. Rebinding is not a permission expansion; permission changes do not automatically resume previously denied resource operations.
- scheduled-tasks::CON-001/AC-04: First-release task output is plain channel text with supported web source links, not executable markup, embedded forms, automatic media downloads or a new host renderer. A valid body within the output budget is chunked for the channel without ellipsis truncation. Each submitted part retains its own outcome; partial acceptance, an uncertain part, or stopping after accepted parts prevents automatic replay or continuation of that occurrence. Check live permissions/pause before every new part. Output beyond the total budget follows scheduled-tasks::QR-001/AC-03; chunking cannot bypass that bound.

## Failure modes and boundaries

These sequences reuse the acceptance units above; they do not define duplicate requirements.

One-time completion sequences: creation → due claim → generating → cache saved → channel wait → sending → accepted; query at every transition; restart/rebind after accepted; interrupted execution/submission; failed/partial/rejected result; empty active view with completed history; completed-name collisions; paging mixed current/completed tasks; foreign-conversation lookup; replay creation after completion. Expected behavior follows scheduled-tasks::REQ-011/AC-01–AC-03 and the existing no-replay/original-target constraints.

| User/event sequence | Observable boundary and authority |
|---|---|
| Describe a task with no time, an impossible date, zero interval, ambiguous “next Friday”, or unsupported action | Clarify/reject without writing half a task: scheduled-tasks::REQ-001/AC-03, scheduled-tasks::REQ-001/AC-04, scheduled-tasks::CON-001/AC-02 |
| Retry a creation whose durable write succeeded but reply was lost | Reuse the stored operation identity without another task; show its current lifecycle and next execution: scheduled-tasks::REQ-005/AC-01, scheduled-tasks::REQ-011/AC-03 |
| Two tasks have the same name, or a reference belongs to another conversation | No guessed mutation or cross-recipient lookup: scheduled-tasks::REQ-001/AC-02 |
| Edit at the moment a task becomes due; edit again using stale settings | Atomic claim/revision boundary: scheduled-tasks::REQ-002/AC-01, scheduled-tasks::REQ-002/AC-02, scheduled-tasks::REQ-005/AC-01 |
| Disable during generation or delivery, receive new session context, then enable | Persist in-flight settlement, do not automatically send while paused, and resume only eligible caches: scheduled-tasks::REQ-003/AC-01, scheduled-tasks::REQ-003/AC-02, scheduled-tasks::REQ-007/AC-02 |
| Run-now while paused or while already executing; attempt deletion while busy | Manual result has scoped authorization; no overlap; deletion guard: scheduled-tasks::REQ-004/AC-01, scheduled-tasks::REQ-004/AC-02, scheduled-tasks::REQ-005/AC-02 |
| Restart before claim, after claim, after body persistence, or during submission | Unclaimed latest slot may start; uncertain execution stops; cached output survives; uncertain sending cannot replay: scheduled-tasks::REQ-005/AC-01, scheduled-tasks::REQ-005/AC-02, scheduled-tasks::REQ-005/AC-03, scheduled-tasks::REQ-006/AC-02, scheduled-tasks::REQ-007/AC-03 |
| Service misses several slots, including across timezone transitions | Latest-only downtime handling differs from intentional pause; caches keep original order: scheduled-tasks::REQ-001/AC-04, scheduled-tasks::REQ-003/AC-02, scheduled-tasks::REQ-005/AC-02, scheduled-tasks::REQ-007/AC-01 |
| Rebind then refresh, refresh then rebind, or rebind a different account | Reconcile only the original target, using current prerequisites: scheduled-tasks::REQ-007/AC-01, scheduled-tasks::REQ-007/AC-02 |
| First cached submission fails, is partial, or has unknown outcome | Stop the drain; do not replay terminals; clear stale blockers accurately on later context: scheduled-tasks::REQ-007/AC-03, scheduled-tasks::REQ-007/AC-04, scheduled-tasks::REQ-008/AC-02 |
| Migrate an existing news task twice or restart mid-migration | Retain one task/occurrence owner and original stored output: scheduled-tasks::REQ-009/AC-01, scheduled-tasks::REQ-009/AC-02 |
| The same incoming reminder is also considered by the memory curator | Only one effective reminder: scheduled-tasks::REQ-010/AC-01, scheduled-tasks::REQ-010/AC-02 |
| A fetched article asks the assistant to change schedules, send elsewhere or execute a script | Treat it as task content, not authority; no recursive scheduling or elevated effect: scheduled-tasks::CON-001/AC-01, scheduled-tasks::CON-001/AC-02 |
| A task result contains links, markup, media URLs, or excessively long text | Text-only rendering, bounded complete output and part-level settlement: scheduled-tasks::CON-001/AC-04, scheduled-tasks::REQ-006/AC-02, scheduled-tasks::REQ-007/AC-03, scheduled-tasks::QR-001/AC-03. |
| Storage unavailable or corrupt; account disabled; access revoked | No false success or unrecorded execution; report/reconcile before advancing: scheduled-tasks::REQ-001/AC-03, scheduled-tasks::REQ-005/AC-01, scheduled-tasks::CON-001/AC-03 |
| Manual execution → disable before sending; disable → manual execution → disable again | Latest pause revokes previous manual grants; already submitted effects settle: scheduled-tasks::REQ-003/AC-01, scheduled-tasks::REQ-004/AC-01 |
| Submit on old context → receive fresh context → old attempt fails | Record old failure, immediately recompute current readiness and wake recovery: scheduled-tasks::REQ-007/AC-02, scheduled-tasks::REQ-007/AC-04 |
| Refresh → rebind clears context; or rebind/refresh → old authentication failure | Require context belonging to current credentials; old auth failure cannot invalidate newer binding: scheduled-tasks::REQ-007/AC-02 |
| Two tasks recover together; older task paused; first part accepted then disable | Shared eligible order, skip paused task, retain partial terminal outcome and stop additional parts: scheduled-tasks::REQ-007/AC-01, scheduled-tasks::CON-001/AC-04 |
| Create interval → slow completion → pause/resume → edit content → edit period | Fixed anchor and explicit new cadence only on time-rule edit: scheduled-tasks::REQ-001/AC-05 |
| Channel unavailable for days → quota reached → manual request → space freed | Refuse new admission at capacity, preserve pending bodies, wake latest-only eligible generation: scheduled-tasks::QR-001/AC-01, scheduled-tasks::QR-001/AC-02 |
| Generate oversized body; disk fails during save; prune terminal history; import over quota | No truncated/unrecorded send, pending content protected, old claims remain closed, imports preserved: scheduled-tasks::QR-001/AC-03, scheduled-tasks::QR-001/AC-04 |
| Delete scheduled reminder → memory extraction replays original message | Durable intent ownership excludes linked duplicate; unrelated plans survive: scheduled-tasks::REQ-010/AC-01, scheduled-tasks::REQ-010/AC-02 |

Reminder wording sequences (scheduled-tasks::REQ-012/AC-01–AC-06): ordinary creation → stored-body preview → due delivery; explicitly quoted payload with spaces/newlines → byte-preserving delivery; nested quote/third party/negation/language/deadline interpretation → clarification where necessary; empty, missing or oversized body → no mutation; content edit while paused or after claim → future body only; rename/time edit → unchanged body; restart/context recovery → exact old cache; legacy task → metadata edit → explicit content edit; replay with a different generated paraphrase → conflict rather than overwrite. Reminder content remains inert text under scheduled-tasks::CON-001/AC-02 and AC-04. Relative deadlines are resolved against the request context; unsupported occurrence-relative dynamic content requires clarification rather than pretending a static body will update itself.

History sequences (scheduled-tasks::REQ-008/AC-01–02): mixed imported/automatic/manual identities → newest execution on the first page; retained history exceeds 31 → each distinct execution remains counted and inspectable; pending protected records exceed 31 → retain them; query a specific occurrence with its task identity → exact outcome; wrong task/foreign conversation/missing occurrence → scoped not-found, never infer absence from an unexhausted page.

Task authority sequences (scheduled-tasks::REQ-013): an old restrictive conversation/memory followed by a relaxed live task and a run-only paraphrase; a negated edit request; explicit field edit plus execution; scope-only edit preserving cadence/pause/body; stale revision after a concurrent edit; a task setting and unrelated preference in one message; ambiguous old memory match; unbound/foreign task reference; interrupted retirement, retry and restart; deleted task with retired memory. Preserve current settings unless the current request authorizes an edit. Retired text and fetched content remain historical data, never mutation authority. A prompt is not a deterministic semantic authorization guarantee; host schema/revision/source checks do not prove edit intent.

Retention sequences (scheduled-tasks::REQ-014): execute 33 times → page every summary → restart → replay the first request; skip a recurring range → count only actual executions; old task with pruned history → known-minimum disclosure; retain pending output past age/capacity → refresh and send exact bytes → start its settlement age; accepted/partial/unknown/rejected/deleted execution → detail expiry → unchanged outcome and no replay; oldest details across tasks exceed capacity → reclaim only eligible details; archive/notification work pending → protect → settle → become eligible; upgrade/reopen twice → idempotent metadata and preserved summaries; invalid limits → fail initialization without cleanup. Detailed payload remains inert text under CON-001; no new rendering capability.

## Implementation Decisions

The model in [ADR-0015](../adr/0015-durable-scheduled-reminders.md) separates these responsibilities: a scheduled task is the durable editable instruction plus time rule and trusted destination; an occurrence freezes one settings revision; an execution result is distinct from a delivery attempt. The task is not itself a Workflow Run. Existing Workflow Runs and Effects remain the authority for their side effects.

Management operations return durable structured results to the main model loop, following the separation in ADR-0008. A timer wakes a service-owned scheduler; it does not ask a model to keep time. The daily-news template retains its reviewed content/retry behavior under the common management boundary. Durable mutation/occurrence claims and atomic migration are implementation prerequisites, not alternative product requirements.

Logic review models enabled → paused → enabled and deletion after settlement. Execution runs → succeeded/failed/unknown/skipped. A successful execution preserves a cached body; explicit deletion cancels pending delivery without rewriting attempts; otherwise delivery is ready → sending → accepted/partial/rejected/unknown or a recoverable prerequisite wait → ready. A task pause overlays eligibility without deleting these facts. Historical attempt failures and current delivery blockers are separate: a freshly satisfied prerequisite can make the body ready while the failed attempt remains visible. Credential generation, context generation and pause generation are different ordering domains; wall-clock timestamps alone do not establish their precedence.

### Task settings and historical memory

The task-authority amendment in ADR-0015 makes current task reads authoritative for execution and reporting. Main-turn tool instructions distinguish the current request, persisted configuration and historical preferences without a phrase table or a second intent classifier. The existing memory curator handles only memory ownership: host-scoped task identities allow it to retire task-only settings or retain the independent portion of a mixed memory. It cannot edit tasks. Retirement and its audit record commit atomically, with optimistic memory revision checks and existing idempotent batch receipts. Fresh curation must not copy task settings back into active memory. Unclassified legacy memory remains historical context until reconciled; its text cannot authorize a task edit. The existing asynchronous curator receives up to 100 task identities from the account and originating conversations, plus the complete bounded active memory set (at most 200 entries / 12,000 characters). It does not receive a parallel task configuration. Explicit correction may retire only its bound memory target; forgetting retains the existing single-remove policy. Retirement updates active lexical/vector search state with the same transaction. A durable normalized-value tombstone prevents exact retired values from being re-added; paraphrased ownership remains a semantic curation responsibility. This is not a startup-wide cleanup or a deterministic guarantee about all model interpretations.

### Researched-text execution

The bounded research amendment in ADR-0015 uses a fresh isolated execution for each occurrence. The main turn saves a research instruction and a fixed template choice; it does not synthesize a static reminder body or an advance report. Existing tasks without a template choice keep reminder behavior, and edits cannot switch the template.

Research must complete actual web search and source-page opening before a report is accepted. The output is complete prose plus numbered HTTP(S) sources, within the existing total UTF-8 body budget; missing search/read evidence, invalid sources, truncated or oversized output fails without a substitute deliverable. Completed tool calls establish retrieval evidence, not semantic truth of every generated claim. Research is independent of channel credentials/context: an eligible task can finish and cache while delivery waits.

The isolated process enables only the approved web execution host while retaining disabled local-resource, shell, plugin, recursive-task and outbound capabilities. Deadline/revocation stops the process; late output cannot overwrite a fenced occurrence. Long research renews ownership and permits unrelated eligible cached delivery and short reminders under the shared capacity limit. Research traces correlate task/occurrence/revision with process startup, completed search/read calls, failure cause and the output-persisted checkpoint. That checkpoint follows the storage commit and does not imply channel acceptance.

### Shared dispatch and migration protocol

These operational rules implement scheduled-tasks::REQ-007/AC-01, scheduled-tasks::REQ-009/AC-02 and scheduled-tasks::REQ-010; they do not introduce another sender or a second set of acceptance IDs.

The trusted recipient is the dispatch key across all scheduled tasks, including imported news. Selection, durable claim and current authorisation checks have one serialisation boundary with task mutations. A claimed external submission may settle after a later pause; each subsequent chunk needs a new live check. Generation can continue under its separate capacity budget. Existing unrelated chat replies/memory follow-ups are outside the scheduled-result chronological guarantee; an explicitly scheduled reminder is excluded from memory delivery by its durable intent-ownership link. Claim fencing must be enforced by every participating sender; a stale worker may record a receipt for its captured attempt but cannot claim another send. A claim/lease timeout is not evidence of zero acceptance: an unreconciled submission becomes terminal unknown before another worker advances. Persisting a later outcome cannot erase newer binding/context or task mutations.

| Ownership phase | Allowed owner and interruption behavior |
|---|---|
| Before fencing | Legacy owner only; new owner cannot claim execution or delivery |
| Legacy fenced/stopped, work settling | Neither owner starts new work. Reconcile captured attempts; use unknown when authoritative outcome cannot be obtained |
| Import prepared but ownership commit absent | Remain fenced with zero active owners and a visible reconciliation status; retry idempotent import, never start both |
| Durable import and ownership commit complete | New owner only; restart resumes it, legacy retry/drain/generation remains fenced; no automatic fallback |

Import maps trusted account, recipient and original news occurrence identity to one stable managed identity; preserve exact message bytes, settings, pending status and every known attempt outcome. Do not infer deleted history. If the legacy process cannot enforce fencing, verified process stop plus exclusive service activation is a cutover prerequisite; a new lock ignored by legacy code is insufficient. A prepared import is not an activation signal. A pre-commit rollback requires verifying that the new owner never activated before explicitly restoring legacy ownership. The ownership commit, not a timer or model response, selects the active owner. [ADR-0016](../adr/0016-daily-news-owner-handoff.md) records the verified stop, durable source fence, transactional import and single-owner activation. Existing news controls and conversational tools project the same committed records. A pending handoff reports reconciliation rather than claiming a complete empty list.

### Specialised daily-news execution

The migrated task defaults to 08:30 Asia/Shanghai and keeps its original recipient. Its name, instruction and schedule use the common revision/lifecycle rules; the news template remains fixed. News keeps its existing complete summaries, archive, actual-execution 24-hour window and same-Shanghai-day no-output research retries after 10, 30, then 60 minutes. Nonblocking archive work has separate bounded local retries under the [daily-news contract](daily-ai-news.md). An explicit retry reuses the failed occurrence and preserves an already scheduled future retry time. Pause or deletion clears future retries; re-enable chooses a future recurring slot. Unknown executions and terminal submissions are never retried automatically.

Successful article results and the complete outgoing body are saved before independent archive work or delivery. Archive failure does not withhold a valid report; cached delivery never researches again. Retain today's retryable automatic news failures outside the settled-detail cleanup set until they settle, are deleted, or leave the same-day retry window. Preserve all imported pending bodies even above quota. Historical failures remain history and cannot be presented as today's retry schedule.

Explicit preview is local preparation, has no scheduled recipient or reserved delivery slot, and shares the two-generation limit. Explicit preview submission reserves its exact cached bytes and uses the common dispatcher; an unavailable submission settles terminally and is not automatically retried. A new preview in progress blocks submission of an older preview. This preserves the existing separate manual-send authorization.

### Reminder wording contract

The existing main model performs normalization during creation/content editing. The host stores a complete receiver-facing body separately from the semantic instruction and exact source/provenance used for ownership. Natural and verbatim modes distinguish semantic rewriting from exact payload preservation. The presence of the saved body distinguishes the new contract from legacy tasks. No per-tick language model or bulk migration is introduced. New create/content-edit requests require a final body after durable replay lookup; older stored operation receipts keep their original identity. Preview fields share the existing result budget, prioritising the outgoing text and exposing omitted content through paged reads. Body preview and paged access use stored text, not a second paraphrase. Existing claim/revision/cache and bounded delivery rules apply unchanged.

### Recurring reminder representation

Fixed intervals persist a first instant and an integer duration. Calendar reminders use one minute-precision local time and all or selected weekdays (Sunday through Saturday) in an IANA timezone. They do not interpret cron strings or monthly rules. The host rejects settings whose first or following execution cannot be represented as a date; it does not impose an arbitrary maximum interval. A calendar rule subject to a stricter configured minimum is checked across a seasonal cycle.

The durable cursor advances in the same transaction as the occurrence claim and any compact skipped range. Occurrence identity includes the task, cadence revision and planned instant; settled-detail cleanup does not move the cursor backwards. Name/content edits retain the cadence; rule or calendar-timezone edits establish a new future cadence and clear obsolete admission blockers. Manual admission respects older eligible automatic candidates under the same two-execution limit.

Examples clarify scheduled-tasks::REQ-001/AC-05, using one timezone and no explicit start:

### Execution summary retention

The retention amendment in ADR-0015 replaces count pruning with permanent summaries and expiring detail within the same atomic occurrence record. Query indexes support newest-first SQL pagination and counts without hydrating every historical body. Detail age starts at eligible settlement, not the planned instant. This is a logical payload budget, not a cap on the whole SQLite file: summaries, protected work, article assets and SQLite free pages are excluded. Existing notification identities and outcomes remain durable. OTel diagnostics keep their independent existing retention policy.

## Testing Decisions

Use the existing fixture-only Weixin inbound simulator for conversational management and observable receipts, following the production inbound chain. Use the scheduler's injected clock/store/channel seams for due time, downtime, restart, migration, blocked prerequisites and outbox ordering. Exercise both orders of pause/manual intent, refresh/in-flight failure, binding/context updates, two tasks recovering in one recipient, each migration crash phase, clock examples, output/quota reservations, over-quota import and settled-detail cleanup. Include crashes between the ownership and send claims, late callbacks and multiple workers; an in-memory happy path cannot establish durable exclusivity. Do not substitute direct Provider calls or manual Run editing for the user path. External results must be distinguishable from fixture responses.

Conflict-context regressions must observe the actual main-model tool sequence, saved settings/revision and occurrence, including explicit-edit controls. Scripted tools verify wiring only and cannot establish semantic preservation. Existing isolated research-process restrictions continue to exclude management tools.

The logic model can answer lifecycle questions only; it does not verify natural-language interpretation, calendar calculation, disk durability, concurrent processes, migration, real credentials or phone delivery. Production implementation requires lint, typecheck, unit/integration and both E2E suites, plus the project's user-confirmed real Weixin acceptance.

## Out of Scope

Proposed first release does not add a client dashboard, arbitrary shell/program execution, cross-account destination management, autonomous permission grants, automated replay of uncertain sends, or full OpenClaw runtime compatibility. Adding a new template remains a reviewed capability change; arbitrary wording does not install new capabilities.
