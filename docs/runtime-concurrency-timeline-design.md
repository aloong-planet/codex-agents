# 运行状态并行时间轴设计

## 目标

现有运行状态按阶段纵向列出，容易被理解为严格串行。页面需要用真实时间戳表达以下关系：

- `typing_start` 请求先于 Codex 处理完成；
- 微信“正在输入”状态在启动成功后持续覆盖 Codex 处理；
- Codex 完成后，`typing_stop` 与最终回复发送可以并行；
- 逐阶段耗时与脱敏诊断归入对应泳道，不再在时间轴下重复一套串行列表。

## 数据与 seam

不修改后端状态结构。浏览器端只读取现有 run 中的：

- `timings[].stage/startedAt/completedAt/durationMs/outcome`；
- `typingDiagnostics.sendStart.outcome`。

纯计算 seam 把 run 投影为时间轴、前置步骤、泳道状态和默认选择模型。它不读取账户、目标、正文、token、URL、ticket 或响应内容。DOM 以该模型决定阶段归属，再复用既有脱敏诊断数据填充展开明细。

## 视觉模型

运行卡片把 `inbound`、`queue`、可选的 `acknowledgement` 和三条主泳道放入同一个阶段列表。前置阶段仍各占一行，使用与主泳道相同的标签、时间条、耗时和状态列，但不可展开：

1. **入站接收**：从腾讯事件时间到本地完成安全持久化；
2. **本地排队**：从安全持久化完成到该目标 FIFO 开始执行；
3. **发送处理回执**：只在正在输入启动失败时出现，单独显示，不并入接收或排队；

随后是三条可展开主泳道：

1. **微信正在输入**：启动请求、状态持续、关闭请求三个相邻片段；只有 `sendStart` 成功时才画“状态持续”。
2. **Codex**：对应 `agent` 的真实起止时间。
3. **微信最终回复**：对应 `outbound` 的真实起止时间。

所有阶段共享同一个横轴。页面只保留简短说明：“时间条按真实起止位置对齐，点击阶段查看明细。” 不再重复解释 typing 内部结构或单独报告某一对阶段的重叠毫秒数。

泳道标题、时间条、总耗时和状态位于同一个可点击的 `summary` 中，展开后原位显示该泳道明细：

- typing：启动、状态持续、关闭，以及 ticket/getconfig/sendtyping；启动失败时明确显示“未启动”，不伪造关闭阶段；
- Codex：App Server、首次模型事件、推理、工具与最终生成；
- 最终回复：准备、sendmessage、读取响应、保存状态与请求次数。

同一 run 一次只展开一条泳道。只要 Codex 泳道存在，默认展开 Codex；Codex 不存在时不默认展开其他泳道。用户手动选择按 run 保存在浏览器内存中，后续轮询重建 DOM 时保持选择。

## 边界与失败模式

- 缺少足够时间戳的旧记录：不显示时间轴，回退到现有详细列表。
- 运行中阶段没有 `completedAt`：用当前时间计算临时终点，但不得超过运行卡片当前横轴。
- typing 启动失败或不可用：只显示启动请求，不伪造“状态持续”。
- stop 缺失：运行中的记录延伸到当前时间；已完成记录最多延伸到 run 的完成时间，避免刷新后继续增长。
- 只有一条有效泳道：隐藏时间轴，因为它无法表达并行关系；详细列表仍正常显示。
- 阶段很短：设置最小可见宽度，但位置仍由真实时间决定；文字放在泳道标签区，避免改变比例。
- 时间戳异常、结束早于开始：丢弃该片段，不让负宽度破坏布局。
- 时间轴只表达客户端已记录的时间，不推断腾讯服务端内部阶段。
- 用户展开泳道后服务轮询：重建 DOM 时恢复该 run 的选择，不跳回默认泳道。
- 新 run 替换旧 run：展开状态以 `runId` 隔离并清理，不把旧选择错误复用到新任务。
- 键盘与辅助技术：使用原生 `details/summary`，保留焦点与 Enter/Space 操作语义。

## 验证

1. E2E 用合成时间戳验证 typing 状态覆盖 Codex，stop 与 outbound 的重叠时长正确。
2. fixture 页面验证默认只展开 Codex、点击后仅展开一条、轮询重绘后保持用户选择。
3. 验证入站、排队和可选回执各自独立显示且视觉结构与主泳道一致，旧记录仍有串行列表回退。
4. 浏览器视觉验收桌面宽度和窄屏布局。
