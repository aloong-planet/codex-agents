# 文件同步错误边界与故障测试

日期：2026-09-08。

## 根因

LocalFileTools 的沙箱调用有错误转换，调用返回后的宿主 `durabilityBarrier` 却直接抛出操作系统异常。独立子进程在真实文件修改之后，对 `fsyncSync` 注入带合成路径的 EIO，经公开工具接口观察到原始错误，而不是现有的 `local_file_mutation_failed`。

外层 WorkflowToolHost 原本会把不受支持的错误转换为通用内部错误，本次没有复现微信泄露路径。缺口在内层公开文件工具错误契约不一致，不能夸大成已发生隐私泄露。

## 为什么原测试没发现

上一轮 SIGKILL 在文件和目录同步均成功之后，仅验证“文件已落盘、日志尚未完成”的恢复。它不会产生 fsync 的失败返回，也不能验证恢复时若同步持续失败是否仍然拒绝记为完成。正常读写测试与版本冲突测试同样没有到达该系统调用失败路径。

## 防御

- 持久化屏障统一转换错误，保留抛出失败、关闭描述符、完成日志在同步之后的顺序。
- 新增12个真实宿主子进程用例：三种修改乘以文件/目录同步错误、两处宿主同步前SIGKILL。每项恢复再注入一次目录同步错误，最后解除故障，验证同操作不重复修改。
- 新增3个真实沙箱用例：临时文件同步注入EIO，验证原目标保持、描述符关闭、本次临时文件清理，解除故障后正常写入。
- 两类省略同步的故意错误确实被测试检出；修复回归不采用从版本库还原整个文件的方式。

临时脚本最初使用 macOS `/var` 别名，Node Permission Model 在加载脚本前拒绝；另有一次 TypeScript 重载未收窄。二者都是测试搭建失败，不能当产品缺陷的有效红测。使用临时目录 canonical path 及显式类型收窄修正，未扩大运行时权限。

## 边界

EIO来自系统接口故障假件，进程退出为真实SIGKILL，但未断电、未损坏设备、未在真实微信服务中注入故障。worker 原子替换前被强杀的残留清理和完整持久化窗口仍需单独核销。当前行为以 spec FM-31/32 为准，运行证据见 [本轮报告](../.workings/app-server-agent-loop/ticket06-sync-failure-test-report.md)。
