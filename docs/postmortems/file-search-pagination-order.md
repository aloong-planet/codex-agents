# 文件查询分页排序不一致复盘

## 故障与根因

2026-09-06，两个文件 Z.txt、a.txt 使用 limit=1 查询时，第一页和第二页都返回 Z.txt。固定沙箱先按 JavaScript 字符串字典序取每分区前缀，宿主再按 localeCompare 重排；前缀集合随页数增长，顺序却改变，offset 因而不再指向同一个全局序列。find 和 grep 均受影响。

另一个稳定性问题出现在不同目录的同路径、同时间文件：最终平局按每个回合随机生成的 scopeRef 决定，新回合可能选择不同文件。

## 原有检查为什么没拦住

原分页样本没有同时覆盖大小写混合、沙箱前缀与宿主合并；同路径同时间的跨目录平局也没有驱动新回合。单次查询排序正确并不能证明下一页不重复。协议返回固定结果更不能检验两个实际排序器是否一致。

## 已落防御

两个查询路径统一使用 UTF-16 字符单元字典序，以稳定 moduleId/scopeId 打破路径平局。模型仍决定排序字段、方向与 limit，宿主不替模型选择业务参数。

公开 LocalFileTools + 真实沙箱回归覆盖四种排序字段、两个方向、逐页与完整结果一致、同/跨模块新回合、grep 页序。真实模型微信 fixture 入口补充“每页1条，全部翻完按序发送”测试，断言两份原文件各发送一次且顺序正确。跨分区扫描不完整另以真实预算和变异核验，防止局部结果被当成全集。

目录发生修改时，offset 游标并不是冻结快照；本次只保证目录未变化时排序一致。fixture 外发不等于腾讯渠道接受或手机收到。
