# ADR-0008: 分离内联文件操作与终止型工作流

- 状态: 已接受(2026-09-03)

## 背景与问题

ADR-0007 确立了主微信 Codex 直接使用受限文件工具且不再设置 Resolver，但仍把所有本地写入都映射成 Workflow Run。该做法会在第一次写入时终止标准 Agent 工具循环，也与 Engine 的单触发单运行约束冲突，因此需要进一步区分本地确定性操作与需要暂停、恢复或对外产生不可确认结果的工作流。

## 备选项

1. **文件查询与本地修改在主模型回合内执行，只有微信外发与待选交互进入终止型工作流**
2. 所有写入和外发都创建 Workflow Run——会使修改后读取、验证和发送无法在同一模型回合内继续，并迫使一个微信触发产生多个运行
3. 所有工具调用都直接返回模型继续——会让外部发送结果由模型自由表述，并削弱 Pending、Effect ledger 与 unknown 不自动重发语义
4. 为本地写入另建独立 Resolver 或文件 Agent——会恢复第二个语义 owner，违背 ADR-0007 已确认的无 Resolver 方向

## 决策

选定**方案 1**：模型可见工具按执行语义分为内联查询、内联修改和终止型工作流。`files.find`、`files.grep` 与 `files.read` 是内联查询；`files.edit` 与 `files.write` 是内联修改；它们都把结构化结果返回主微信 Codex 并允许同一回合继续。内联修改由 Local File Tools 隐藏持久操作日志、CAS、prepare/commit、原子替换与崩溃对账，不为每次修改创建 Workflow Run。

`weixin.send_files` 是终止型工作流。已选文件只有在不可变发送快照及其 manifest 持久化且 Run 被 Engine 接受后才转移 Owner；待用户选择时只持久化候选身份、revision、Input Gate 与 Run，用户选择后才生成发送快照。预检失败不转移 Owner，而是把结构化错误返回模型继续处理。每条微信入站最多接受一个终止型工作流。

文件引用的认证身份与实时可用性分开处理：宿主先从引用中取得账户、模块、scope、相对资源身份和签发版本，生成稳定操作键并查询日志，再校验当前权限和文件状态。收窄读取权限时递增账户的访问上下文代际，并轮换其已启用目标的 App Server thread，防止旧文件正文继续留在可恢复的模型上下文中。

## 后果

- 正面: 主模型可以在同一回合连续查找、读取、修改、验证并最终发送文件，交互形态与通用编码 Agent 一致。
- 正面: 本地确定性修改可以用内容 hash 对账；外部发送继续保留持久 Run、逐项 Effect、Pending 和 unknown 不自动重发语义。
- 正面: 预检错误仍可由模型修正，只有已经建立持久工作流的请求才取得最终回复所有权。
- 负面: Local File Tools 需要宿主侧操作日志及沙箱内部 prepare/commit 协议，并需要处理修改成功但工具结果未返回的恢复窗口。
- 负面: 收窄读取权限会轮换相关微信目标的模型 thread；旧会话中的普通短期上下文不会自动复制到新 thread。
- 负面: 首版每个微信入站只支持一个终止型工作流；同一回合编排多个彼此独立的外部工作流需要后续专门设计。
- 中性: Node Permission Model 只作为可信固定文件实现的纵深防护，不承诺运行不可信代码时的强安全隔离。
