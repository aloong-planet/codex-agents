# ADR-0009: 由主模型迭代文件查询，宿主不作语义改写

- 状态: 已接受(2026-09-04)

## 背景与问题

ADR-0008 已确定文件查询在主微信 Codex 回合内执行，但真实微信请求证明，一次由模型生成的过窄查询仍可能在文件存在时返回零候选；当前协议测试又用固定结果替代真实搜索，无法暴露这种偏差。系统需要提高自然语言查找的召回率，同时继续保持主模型唯一语义 owner、无 Resolver 和宿主不解释业务意图。

## 备选项

1. **把每次搜索结果回灌主模型，由主模型在同一工具循环中改写查询；搜索器只提供通用 Unicode 归一化与机械模糊匹配**
2. 零结果后调用独立模型 Query Rewriter——会恢复第二个文件语义 owner，增加延迟、超时和上下文分歧
3. 宿主维护“文件、原文件、笔记”等停用词并自动删词——覆盖依赖业务枚举，容易误删真实文件名语义
4. 引入 embedding/向量语义检索——当前规模与目标不需要，且会引入索引一致性、模型迁移和额外资源成本

## 决策

选定**方案 1**：`files.find/files.grep` 的候选、零结果、截断、扫描不完整和可修正错误都返回同一个主微信 Codex 回合；主模型根据用户原意自行决定后续 query、模式、范围和是否继续。宿主不将单次零结果变成终局，不运行独立 Query Rewriter，也不按业务词表改写查询。文件搜索器只执行 NFKC、大小写、空白/标点及 Unicode 字符体系边界切分、相关度排序、授权和预算校验。

模型可见工具说明必须用通用原则指导查询提炼和零结果重试，不枚举应删除的业务词。生产等价模型测试必须执行模型实际生成的参数并返回真实搜索结果；固定候选 stub 只能验证协议布线，不能作为自然语言查询验收。

## 后果

- 正面: 行为与 Claude Code、Codex 的标准 agent tool loop 一致，拥有完整对话的主模型可以观察结果后自行修正。
- 正面: 无空格的中英混合输入获得通用容错，不需要为笔记、图片或未来文件类型分别维护规则。
- 负面: 文件查找可能增加一至数次模型工具往返，并继续存在模型选择不重试的概率，需要通过契约、eval 和观测持续改进。
- 负面: 部分 term 模糊命中会扩大候选集合；系统必须保持稳定排序、多候选确认和扫描完整性语义，不能把高分当成唯一确定性。
- 中性: 权限、路径 containment、预算、opaque reference、发送快照、Input Gate、Effect ledger 与 unknown 不重发语义不变。
