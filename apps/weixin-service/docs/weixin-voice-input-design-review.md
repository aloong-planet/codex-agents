# 微信语音入站设计审查

## 审查结论

方案可以实施。审查后保留“腾讯转写 → 文本 Codex turn”的窄链路，不引入媒体下载或新的外部凭据。

## 发现并纳入设计的问题

1. **不能把无转写语音伪装成文本交给 Codex。** 固定拒绝事件必须与可处理文本事件分开，否则模型可能把“无法识别”当成用户指令继续生成回答。
2. **60 秒限制必须在协议层、调用 Codex 前执行。** 对缺失或非法 `playtime` 采取 fail-closed，避免上限只存在于 UI 文案。
3. **语音仍必须捕获消息级 context token。** 回答不能稍后从可变 target cache 读取 token，否则快速连续消息可能串用上下文。
4. **拒绝事件也需要去重。** 若只对 Codex turn 去重，getupdates 重放会重复发送“无法识别”提示。
5. **面板标记与模型输入必须分离。** 面板保存 `[语音转写]` 以便审计；模型应得到原始转写和明确来源说明，避免标记污染用户原话。
6. **带转写语音应复用现有自动绑定 seam。** 这样第一条可处理语音能建立目标；无转写语音不能触发欢迎语，避免同时发送欢迎和失败两条消息。
7. **不能仅根据 item type 推断时长合法。** `playtime` 的毫秒整数边界要显式校验，60,000 允许，60,001 拒绝。
8. **不应依赖未文档化的 App Server `localAudio`。** 本机生成类型不等于稳定产品承诺；用户已选择仅用腾讯转写。
9. **不能从腾讯插件内部深路径直接 import。** Demo 不修改插件源码，并保持自己的窄协议解析；本功能也不需要 `silk-wasm`。
10. **语音正文不应进入日志。** 只能在已存在的私有聊天记录与 Codex rollout 中保存，不新增终端打印。

## 被否决的方案

- **把加密媒体 URL 直接交给 Codex**：需要认证和解密，且会暴露协议秘密。
- **依赖实验性 `localAudio`**：官方稳定 turn 输入未承诺，模型支持也可能变化。
- **默认本地 Whisper**：用户明确选择仅使用腾讯转写，且希望避免额外 CPU。
- **无转写时静默忽略**：用户无法判断系统是否收到语音。
- **无转写时让 Codex生成错误提示**：无意义地启动模型，也可能产生不诚实回答。
- **失败后用下一条消息的 token 重发**：可能导致重复或跨上下文发送。

## 实施门禁

- TDD 的高层 seam 为 `DirectIlinkChannel` 发布事件与 `WeixinCodexService` 的公开 transcript/发送结果。
- 真实语音只在所有自动测试通过后由用户亲自发送；测试期间使用不含真实凭据和媒体 URL 的合成 getupdates fixture。
