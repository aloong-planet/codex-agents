# Memory Curator 尝试诊断设计审查

## 审查结论

方案可实施，复杂度集中在已有 `AccountMemorySystem` seam 内，没有让微信入口、Curator agent 或页面承担错误持久化职责。

## 已补齐的问题

- **重试成功覆盖失败**：尝试历史与当前 `error` 分离；成功只清理当前错误，不删除历史。
- **异常泄密**：不保存原始异常，只保存稳定允许码或统一未知码。
- **状态膨胀**：任务历史已有 200 条上限，每个任务再限制为 5 次尝试。
- **历史数据误导**：v2/v3 迁移为空数组，页面明确缺少历史诊断，不反推原因。
- **账户停用竞态**：取消仍形成一次失败尝试，但任务回到 `pending`，且没有虚构的自动重试时间或被消耗的重试档位；诊断序号独立递增。
- **时间一致性**：一次状态转换只读取一次结束时间，用同一值计算耗时、更新时间和重试时间。
- **公开状态泄漏**：公开字段不含 job ID、batch ID、账户原始正文或异常文本。

## 拒绝的替代方案

- 只增加服务器 stderr：服务重启后丢失，也无法从页面核对历史。
- 保存完整异常：排障信息更多，但可能带路径、正文、工具参数或上游响应，不符合本地隐私边界。
- 单独建立诊断数据库：当前数据量很小，会新增不必要 seam、事务和迁移复杂度。
- 仅显示 `lastError`：重试成功后仍会消失，不能解决本次问题。
