# Context token 时效实验设计审查

## 结论

设计可实施，但必须守住以下不变量：

1. `ret=-2` 只能表述为“本次 sendmessage 的 context 被拒绝”，不能宣称腾讯正式 TTL。
2. 实验必须绑定 `{accountId, target, baselineContextUpdatedAt}`；任一变化都终止，不能串用新 token。
3. `unknown` 绝不自动重试；明确拒绝的现有内部单次重试必须在结果中可观察，避免误计探针次数。
4. T+48h 要实际执行最后一次探针后才能给出“至少 48h 有效”。
5. 恢复服务时不能批量补发错过的探针，否则既打扰用户也污染次数变量。
6. `caffeinate` 只能改善空闲睡眠，不能承诺合盖、断电和重启后的连续运行。
7. 公共状态不得出现 token、完整原始 ID、消息 ID 或服务器错误正文。

## 审查中补充的设计

- 加入 `probing` 持久状态。进程若在该状态重启，转为 `unknown` 并停止，避免把可能已接受的探针再发一次。
- 探针计划以基准时间的整小时偏移计算；迟到只执行最近一个尚未执行的逻辑序号，下一次仍回到基准时间轴。
- 记录逻辑探针序号和 `retriedSegments`，明确暴露次数混杂因素。
- 日报 run 成功必须通过清理 helper 删除旧失败字段，不能继续用对象 spread 保留旧 `error`。
- 本地通知作为可替换 adapter；失败不改变渠道/调度的权威状态。
- 实现审查发现 FixturePort 原先只有单一 snapshot listener；实验接入会覆盖 DemoService。已改为多订阅集合，并以完整浏览器流程验证别名和页面状态仍会刷新。
- 激活 CLI 必须从当前 snapshot 自动选取最近入站目标并要求显式基准时间，不能读取或打印 token。

## 用户操作序列复核

- 入站后未到 23h：页面显示等待，不发送。
- 23h 探针被接受：页面显示至少 23h 有效和下一次时间。
- 26h 电脑睡眠，28h 恢复：只发第 28 小时探针，不补 26/27h。
- 30h 用户误发新消息：页面显示“本轮被新入站打断”，不再发送。
- 35h `ret=-2`：页面记录约 35h / 第 N 次首次被拒绝；停止。
- 48h 被接受：页面记录“至少 48h 有效”；停止。
- 日报 `ret=-14`：提示重新绑定，不错误要求发入站消息。
- 日报超时：显示未知，不因下一条入站自动补发。

审查后无未决产品决策。
