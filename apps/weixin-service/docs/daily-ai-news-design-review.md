# 每日 AI 新闻微信汇总设计审查

> Historical design/review: scheduling and storage ownership below describe the former dedicated scheduler. Current behaviour is defined by the [daily-news specification](../../../docs/specs/daily-ai-news.md), [scheduled-task specification](../../../docs/specs/scheduled-tasks.md) and [ADR-0016](../../../docs/adr/0016-daily-news-owner-handoff.md). Earlier summary-format proposals in this record are superseded by the complete-prose contract.

## 结论

设计可实现，但实现前必须保留以下约束。所有问题已在设计中闭环，未发现需要新增用户决策的阻塞项。

## 审查发现与修正

1. **把失败都当作可补发会制造重复消息。**
   - 修正：明确拒绝/无上下文才进入 `pending_inbound`；网络异常、超时和崩溃中的 `sending` 一律进入 `unknown`，不自动重试。
2. **只靠 timer 会漏掉进程重启后的当日日报。**
   - 修正：`start()` 同时检查上海本地日期；已过 08:30 且今日无 run 时立即补跑，只补今天。
3. **自动任务与手动测试共用 runKey 会让测试吞掉正式日报。**
   - 修正：自动 run 使用日期 key；手动预览/发送使用独立 `manual-*` 标识，不改变自动幂等判断。
4. **在 AI 返回后再读取最新目标会导致串线。**
   - 修正：每次 run 启动时捕获不可变 `{accountId,target,runKey}`；投递与账本都使用该快照。
5. **入站补发与聊天回复并发会争用可变上下文或打乱顺序。**
   - 修正：日报监听同一入站事件，但补发排入独立串行队列；事件先由通道更新持久化上下文，再通知监听器。补发使用匹配账户和目标的最新通道发送，不读取正文。
6. **只存最终文本无法审计来源与去重。**
   - 修正：账本保存结构化条目的非敏感字段和稳定 item key；页面显示来源 URL，但不显示任何微信凭据。
7. **长链接可能让一条微信消息过长。**
   - 修正：格式器设定 1,500 字符硬上限，按排名逐条纳入；至少保留标题、来源域名和规范 URL。若第五条放不下则诚实显示实际条数，不拆成多条以免部分成功。
8. **把 CLI 检索称为必然实时会产生假承诺。**
   - 修正：生产 adapter 必须显式使用 `--search`，预览展示来源和生成时间；失败时显示失败，不回退到模型记忆。
9. **默认立即启用可能在未验证时产生外部发送。**
   - 修正：功能初始禁用；用户在页面确认目标并点击启用后才安排自动 run。实现验证阶段不代用户点击真实发送。
10. **重复点击或入站补发与定时发送并发会造成重复或状态覆盖。**
    - 修正：模块内所有研究与发送经过同一串行操作队列；手动重复操作立即拒绝，自动 run 在排队前先落账占位。
11. **研究中停用仍继续发送会违背用户意图。**
    - 修正：自动研究完成、进入 `sending` 前再次核对启用目标；已停用或切换目标则记为未发送失败。已经提交给 iLink 的请求无法撤回。
12. **研究阶段崩溃会留下同日占位并永久阻止补跑。**
    - 修正：重启时移除遗留 `researching`/`ready` 并安全重新研究；只有遗留 `sending` 必须转为 `unknown`。
13. **按上海自然日查新闻会漏掉全球上一工作时段。**
    - 修正：每次运行捕获一个不可变结束时刻，检索该时刻向前 24 小时；08:30 正常运行与当天晚些时候补跑都使用各自真实运行时刻。
14. **在项目目录运行 Codex CLI 会加载与新闻无关的规则、技能或子代理流程。**
    - 修正：在权限为 `0700` 的临时空目录运行；显式忽略用户配置与项目规则，并关闭 `skill_search`、`plugins`、`multi_agent`。
15. **`items: []` 是合法 JSON，但不能证明真实搜索发生过。**
    - 修正：启用 CLI JSONL 事件流；必须看到至少一个完成的 `web_search` 才读取并接受最终结构化输出，否则整次预览失败且不覆盖为“无更新”。
16. **提示词要求 24 小时窗口不等于模型一定遵守。**
    - 修正：结果解析阶段再次检查每条 `publishedAt` 可解析且落在闭区间内；任一条越界都拒绝整次结果，不静默混入旧闻。
17. **把上限从 5 改到 10，可能只是得到更多供应商、融资和合作公告。**
    - 修正：prompt 分主题搜索，技术更新优先；素材充足时至少 6 条技术内容，融资与纯商业合作最多 2 条，宁缺毋滥。
18. **从用户消息删除 URL 后仍需要可信核验和稳定去重。**
    - 修正：规范 URL 继续存在私有 digest/ledger；微信格式器和公开状态 DTO 都显式剥离 URL，只显示来源名。
19. **10 条摘要可能突破单条消息长度。**
    - 修正：仍保持单条发送与 1,500 字符上限，按排名尽可能装入 10 条；不自动拆成多次发送，避免部分成功和重复风险。
20. **上限 10 条不代表搜索足够广，模型可能一次搜索后只返回一条公司新闻。**
    - 修正：生产 JSONL 门禁只要求至少 1 个完成的 `web_search`，用于排除完全未搜索的输出；不再把固定搜索次数当作覆盖度代理。主题覆盖仍由 prompt、候选校验、时间窗和来源核验保证。
21. **用近 7 天技术新闻补足数量会重复旧闻并改变已确认的 24 小时语义。**
    - 决策：用户明确拒绝扩大窗口；搜索充分后若只有少量合格内容，则按实际条数展示，不降质、不补旧闻。
22. **一句抽象描述虽然满足 schema，但用户无法理解文章到底做了什么。**
   - 修正：`summary` 必须包含 2–4 个换行重点；方法类文章写主要步骤，分析类文章写关键数字/事实和风险，禁止标题释义。
23. **模型可能对没有读到正文的付费文章生成貌似完整的摘要。**
   - 修正：提示词要求仅纳入已实际读取并可核验正文的文章；无法核验则跳过并继续寻找其他候选。
24. **详细摘要会与单条微信 1,500 字符和 Top 10 同时冲突。**
   - 修正：质量优先于数量；每条必须完整装入，超出总长度的后续条目不加入，绝不截断重点或拆成多次自动发送。
25. **仅要求“搜索技术新闻”会让模型完全不访问 Hacker News。**
   - 修正：增加 `section` 枚举，并要求从官方 HN `topstories`/item API 取当前候选；生产结果缺少 HN 条目时明确失败。
26. **用原文发布日期过滤 HN 会漏掉今天重新进入热榜的旧文章。**
   - 修正：HN 栏目使用官方 item 提交时间校验当前性，且用独立栏目标题避免与过去 24 小时发布新闻混淆；原文仍必须打开阅读。
27. **把综合搜索和 HN 深读塞进单个任务，即使收窄候选、放宽到 240 秒仍会超时。**
   - 后续修正：官方前 10 名按排名交给独立 HN 单篇任务深读，成功 5 篇即停止；单篇失败剔除并顺延。普通新闻使用独立的发现和摘要任务。为保证跨栏目不会重复摘要，HN 先完成，再把成功条目的身份排除出普通新闻；接受相对并行方案的延迟增加，各子任务仍各自受 240 秒超时约束。
28. **成功预览仍显示早上自动 run 的 `failed`，会形成假失败。**
   - 修正：顶层状态表示当前操作/预览就绪状态，历史自动发送结果继续由独立 `lastRun` 字段展示。
29. **自由文本摘要把内容质量与固定前缀、换行符绑定，真实 HN 深读因排版差异被拒绝。**
   - 修正：结构化 schema 使用独立 `conclusion` 与 `points[2..4]`，本地负责统一排版；模型只负责内容，不负责协议符号。
30. **即使“结论 + 重点”都具体，读者仍不知道文章为何出现、结论从何而来。**
   - 修正：用四段语义字段取代平铺要点：先说明背景问题，再写新变化/方法，然后给关键证据，最后说明影响与限制；本地按固定因果顺序渲染。
31. **发送后去重无法阻止同一文章反复生成摘要。**
   - 修正：普通新闻先发现元数据，本地用规范 URL 哈希排除历史，再摘要候选；HN 也在深读前过滤。摘要与其文章 key 先写入账本，归档失败和同日重复预览都复用缓存。
