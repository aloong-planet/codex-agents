# Tokei 深色仪表盘设计审查

## 结论

方案可实施。截图目标是一个深色桌面仪表盘，不是 CLI 终端；以截图替换仓库名称联想后，视觉方向与用户目标一致。实现应保持 CSS 主导，只给 Header 增加无业务含义的装饰节点。

## 审查发现与修正

- **截图结构与现有内容不等量**：截图是四张数据卡，连接页只有三步；采用两列加第三张横跨整行，复用其卡片节奏而不伪造数据。
- **全暗主题可读性**：长中文说明不能使用低对比灰；正文、标签、输入值分别保持三级但足够的对比度。
- **彩色卡片过艳**：色彩仅进入低透明度渐变、边框和状态点，避免整块高饱和背景影响阅读。
- **窗口感挤压移动端**：840px 以下逐步减小圆角和 padding，560px 以下改为全屏壳体。
- **二维码反色风险**：二维码容器固定白色、有 quiet zone，不继承卡片背景。
- **状态语义冲突**：卡片主题色只表示功能分组，渠道状态仍由绿/黄/红文字和边框表达。
- **导航滚动回归**：保留现有固定 Tab 与内容独立滚动结构，不改脚本选择器和 ARIA。
- **视觉测试脆弱**：不对 Hex、阴影或圆角写单测；现有 E2E 验证用户流程，再做真实页面的桌面/移动视口检查。

## 失败路径复核

- 二维码出现时：白底可扫，长说明不会撑破卡片。
- 账户/目标列表很长时：select、原始 ID 和 metadata 可换行或内部滚动。
- 反馈很长时：内容区滚动，Header/Tab 不被顶走。
- 新闻、诊断和 Memory 内容很长时：pre 内部可滚动且不会制造页面横向溢出。
- 浏览器禁用动效或启用高对比时：焦点与分区仍能被识别。

## 测试策略

这是纯视觉调整，精确颜色和圆角没有稳定的行为测试价值，因此跳过这部分 TDD。保留并运行既有 HTTP、交互和 Playwright E2E；实现后审查 DOM 选择器、响应式溢出、focus、二维码白底和动态状态样式。
