# 日报失败微信通知与立即重试设计审查

日期：2026-08-15

## 结论

方案可实现，但必须把失败通知、日报重试和微信命令消费做成三个正交状态，不能用一个 run status 混在一起。

## 审查发现与修正

1. **让 scheduler 和 Codex 都监听同一命令会双回复。** 修正为通道级 `onInboundCommand` 消费 seam；命令一旦命中，普通入站 listener 完全看不到。
2. **依赖 listener 注册顺序不可靠。** 命令 handler 是单独集合，并在普通广播前运行；不通过“先 start scheduler”碰运气。
3. **通知失败不能覆盖日报失败状态。** `failureNotice` 作为 run 的附属状态；run 始终保持 `failed`，后台 timer 仍能识别。
4. **通知结果未知不能自动补发。** 只有 `reason=rejected` 才保存正文并在新入站后补一次；unknown 直接终态。
5. **补发通知的入站可能正是立即重试命令。** 命令已在普通广播前被消费，因此不会先补旧通知再启动新任务；新任务会生成与本次结果一致的新通知。
6. **即时失败若按 attempt 重新退避会违反用户要求。** 私有即时重试流程捕获原 `nextRetryAt` 并作为 preserve 值传入；研究/归档失败时优先恢复该时间，不从即时失败时刻重算。
7. **即时成功但日报发送 rejected 不应恢复研究 timer。** 研究和归档已经成功，run 进入现有 `pending_inbound`；重做研究既浪费又可能重复，因此原 timer 取消。
8. **连续重复命令会并发。** 仅检查 activity 不够，因为异步队列尚未切换 activity 时第二条命令可能穿透；handler 必须同步设置 `commandRetryInFlight`，随后取消 timer 并排入既有 exclusive 队列。忙时只给固定反馈，不排队第二次。
9. **服务重启不能重发已接受或未知通知。** 仅持久化的 `pending_inbound` 可由新入站触发；start 本身不发送通知。
10. **原始异常不能进入微信。** 文案仅由枚举映射生成；不做“脱敏后原文”拼接，未知类也只显示固定文案。
11. **发送失败本身无法可靠用同一渠道告警。** 本版只通知研究/归档失败；正文发送的 accepted/partial/unknown/pending_inbound 继续现有防重复语义。
12. **网页按钮会扩大本次自定义需求。** 用户明确只要求通知提示固定中文回复，且排除 slash 命令；因此不新增 HTTP/UI 重试入口。
13. **确认消息的协议请求可能阻塞立即重试。** “已开始”确认改为异步发送，研究流程不等待它返回；确认失败不会取消用户已经明确发起的重试。
14. **同一入站同时补失败通知和旧日报会产生双发。** 若命中待补的失败通知，本次普通入站只消费这一项；旧日报等待下一条入站，避免一次上下文刷新触发两条外发。

## 审查后的接口

- 通道：新增一个可选 `onInboundCommand(handler): unsubscribe`。
- scheduler：不新增公共方法；命令 handler 与即时重试均为内部实现，其他调用者仍只学习原有接口。
- Demo/HTTP/UI：不新增控制接口。

这保持接口窄：命令分发只负责消费，scheduler 内部承载日期、目标、并发、保留 timer 和结果通知全部行为。
