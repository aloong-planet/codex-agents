# 扫码后自动绑定与首次问候设计审查

## 审查结论

方案可实施，但必须保留下列约束，否则会产生重复外发或错误绑定。

## 已发现并纳入设计的问题

1. **仅观察 target snapshot 不足以触发问候。** snapshot 可能包含历史目标，也不携带触发消息的专属 token；必须使用 `InboundTextEvent` seam。
2. **先发送再记录会留下重复窗口。** 两条消息或进程重载可能重复问候；必须先持久化 `sending` 并清除 pending，再调用 `replyText`。
3. **只在内存中布防无法承受 watch 重载。** 登录成功与用户发首条消息之间可能发生服务重载；pending 状态必须独立持久化。
4. **把问候状态塞进 iLink 凭据文件会扩大敏感模块职责。** 使用独立、无秘密的 `AutoBindingStore`，不修改插件源码或凭据格式。
5. **浏览器按 DOM 旧选择渲染会掩盖服务端自动选择。** 多目标时必须优先服务端选中值，否则后端已绑定、页面仍展示另一个目标。
6. **登录事件没有账户 ID。** 只能在 `port.start()` 后读取 snapshot；仅当存在可用账户时布防，凭据 stale 时保持错误。
7. **问候与 Codex 自动回复可能同时发送。** 这是两个明确独立的功能；本改动不隐式启用/停用 Codex。页面会说明第一次消息可能继续由已启用的 Codex 处理。
8. **发送超时的真实结果未知。** 不把 `unknown` 当明确未发送，也绝不自动重试。

## 被否决的替代方案

- **复用手动 `/api/session/confirm`**：浏览器轮询无法获得消息级 token，且把可信判断放在客户端。
- **发现新 target 即发送**：历史状态、元数据更新和非文本消息都可能误触发。
- **把欢迎语交给 Codex 生成**：增加延迟、故障面与不可预测内容；固定问候更适合连接确认。
- **失败后等待下一条入站自动重试**：可能在第一次请求其实已送达时重复发送。

## 审查后的最终边界

自动绑定只由“新登录已完成 + 同账户第一条真实 USER 文本入站”触发。状态消费先于外发，外发最多尝试一次；绑定选择可继续用于测试消息和后续手动启用的 Codex 服务。
