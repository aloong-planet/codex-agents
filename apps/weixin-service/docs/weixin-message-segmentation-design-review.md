# 微信正文截断与分段发送设计审查

日期：2026-08-14

2026-08-23 回同步：可靠性第二阶段以持久出站账本取代 unknown 自动重试。明确拒绝仍可复用 client ID 重试一次；unknown 禁止重试。

审查对象：`docs/weixin-message-segmentation-design.md`

## 结论

设计可以进入实现。分段必须位于 `sendTextWithContext()` 的最低共同 seam；若只改日报或只在页面切片，入站回复会绕过规则，且各调用方无法一致表达部分成功。

## 审查发现与修正

1. **编号会挤占 1,500 字符。** 不能先切 1,500 再加 `[1/N]`；segmenter 必须先预留最坏编号空间并最终复核。
2. **JS `string.length` 会按 UTF-16 code unit 计数。** 至少按 Unicode code point 切分，避免把 surrogate pair 切成无效文本。
3. **总段数依赖切分，而编号容量又依赖总段数。** 使用最大 8 段的最坏编号预算可得到确定性计划，避免不稳定迭代。
4. **截断标记本身也可能超限。** 第 8 段必须先为标记腾出容量，不能在发送前简单追加。
5. **明确拒绝后的重试必须复用同一 client ID，但使用独立账本 attempt。** 新 ID 会进一步增加重复概率；协议未承诺 unknown 幂等，因此 unknown 不再重试。
6. **凭据失效不应盲目重试。** 用户选择“失败重试一次”，但 `auth_stale` 已证明前提失效；安全上直接停止，作为明确例外。
7. **部分失败不能沿用日报 `pending_inbound`。** 该状态会整篇补发，必然重复前段；新增 `partial` 且永不自动重试。
8. **发送完成不等于手机完整收到。** `acceptedSegments=N` 只表示 N 次 iLink 接受；页面与日志不能宣称手机收齐。
9. **日报当前格式器会静默舍弃条目。** 统一分段前必须移除格式器的 1,500 门禁，否则 segmenter 永远看不到被丢掉的新闻。
10. **Codex 500 字符截断会让统一分段形同虚设。** 模型回答截断上限必须提升，但持久化 schema 也要同步，不能只改一处常量。
11. **HTTP body 是 byte 限制。** 12,000 个中文字符可能超过 16 KiB；测试消息入口需提高到 64 KiB，同时逻辑字符上限仍在业务层执行。
12. **重试会扩大 turn 延迟。** 只有明确拒绝才立即重试；unknown 最多等待单次 15 秒。页面仍须在发送期间保持 sending 状态。
13. **并行发送会破坏顺序。** 段落只能串行；不得为降低延迟使用 `Promise.all`。
14. **不能在失败后继续后续段。** 用户已选择当前段重试一次；第二次失败后仍要停止，避免中间缺口继续扩大。
15. **测试 fake 只返回一个 messageId 会掩盖聚合逻辑。** 通道层测试必须断言实际请求正文、顺序、client ID 和调用次数；调用方 fake 则显式返回完整聚合字段。
16. **运行中的 launchd 服务不会热加载。** 实现和自动测试完成后，需明确重启该单一 Demo job 才能加载新代码；重启前确认没有正在发送的逻辑消息。
17. **聚合结果直接改为必填会破坏旧通道实现。** 类型层将新增字段设为可选，真实直连通道始终完整填充；调用方只对旧实现采用保守默认值，避免为了本功能强迫所有 fake 和外部端口同步迁移。

## 实现顺序

1. 纯 `WeixinTextSegmenter`，边界测试先行。
2. `SendTextResult` 聚合字段与 `DirectIlinkChannel` 串行发送/仅明确拒绝单次重试。
3. Codex、日报、测试消息的长度与 partial 状态映射。
4. 页面反馈与 fixture 行为。
5. 全量 review、测试 review、design 同步。
6. 经验证后只重启 launchd 托管的 Demo job；真实长消息由用户另行确认触发。
